# 开发与调试记录

本文件补充 [开发对话](conversation.md)，按任务阶段记录关键执行与验证，包括失败现象和修正过程。公开副本省略主机路径、账号和认证信息。

## 第一轮：建立平台和首版实验

1. 根据课程要求确立目录输入、动态执行、崩溃报告、开源交付的验收项。比较自制事务工具与现成 jq，确定用现成 jq 作为实验目标。
2. 核对 jq 上游 issue #3348 和修复 PR #3350。官方文件下载发生中断后完成续传，分别按发布 API 提供的 SHA-256 核验 1.8.0、1.8.1。
3. 实现目标清单、独立进程、退出分类、字节和结构化变异、故障去重、同签名缩减及重放。
4. 用正常脚本运行固定种子实验。种子 7 的试跑在第 6 次执行捕获断言，52 字节输入缩减到 2 字节。
5. 比较三组随机种子下的字节级与结构化变异。另测 JSON 边界和排序性质。
6. 首次公开发布，视频由终端输出事件重绘生成。

## 第二轮：修正判定器误报

7. 复核发现：应用的普通错误只要错误文本里出现 `Assertion failed:`，旧判定器就报 `crash`。复现命令：

   ```sh
   printf 'error("Assertion failed: application message")\n' > /tmp/fp.jq
   targets/jq-1.8.0/jq -n --from-file /tmp/fp.jq   # exit=5
   ```

   旧版平台对同一输入返回 `crash`，属于误报。

8. 修正方式：崩溃只由进程异常状态认定（Windows 异常码集合、POSIX 信号），断言文本仅用于给已确认的异常补充签名；ASan 诊断只在目标声明 `address_sanitizer` 时参与判定。修正后同一输入返回 `rejected`。
9. 回归验证：真实缺陷样本仍判为 `crash`（`0xC0000409`，`Assertion failed: end > loc.start, file src/locfile.c, line 82`），修复版返回 `rejected`（exit 3）。
10. 新增 `RunnerTests`：用真实子进程覆盖“断言文本 + 正常退出码”“abort”“超时”“启动失败”“输出截断”“中文与空格目录”等场景，测试数从 8 增至 17。

## 第三轮：确定性用例库

11. 新增 `code/build_cases.py` 生成 `targets/jq-cases/cases.jsonl`。首版一次生成 269 条，直接运行后有 8 条不通过，逐条核对后确认全部是**预期写错**，不是被测程序的问题：

    | 用例 | 原预期 | 实际 | 结论 |
    |---|---|---|---|
    | `"" \| split(",")` | `[""]` | `[]` | jq 对空串返回空数组，与 Python 的 `str.split` 不同，按 jq 语义修正 |
    | 输入 `-0` | `0` | `-0` | jq 保留负零字面量 |
    | 100 元素排序 | `[0, 1, ...]` | `[0,1,...]` | 预期生成用了带空格的 `json.dumps`，改为紧凑分隔符 |
    | 空输入、空对象迭代 | `"\n"` | `""` | 平台对无输出记录的 stdout 为空，预期改为空串 |
    | 数字 `split` | `cannot be split` | `split input and separator must be strings` | 按实际错误文本修正匹配串 |
    | 对象 `join` | 报错 | 正常返回 | `join` 会遍历对象值，改用 `[{"a":1}]｜join("-")` 触发 `cannot be added` |
    | `input_filename` + stdin | `"a.json"` | 空输出 | 从标准输入读取时该内建无输出，改为显式传入文件名参数 |

12. 修正后 1.8.0 与 1.8.1 各 263/263 通过；两版共享的 257 条用例行为完全一致（`results/suite/comparison.json`）。版本相关的 6 对用例按版本分别执行：旧版 `0xC0000409` 断言，修复版 exit 3 语法错误。
13. 平台接口为套件做了三处最小扩展：`Target.run(data, args, files)` 支持逐例参数与辅助文件，`Target.use_binary()` 支持换一个构建运行同一套用例，`summary.json` 增加目标 SHA-256、平台版本和运行环境。

## 第四轮：扩大随机实验

14. 从 3 个随机种子、每次 100 次候选，扩大到 10 个种子、每次 1000 次候选，两种策略共 20000 次执行。`experiment.py` 增加 `aggregate.json`，统计每种策略的命中率、首次发现位置与耗时分布。
15. 首次尝试在扩大规模时进行到一半，因需要统一新增的 `platform_version` 字段而中止并重跑，避免同一批结果中出现字段不一致的实验记录。

## 第五轮：实际屏幕录像

16. 使用 ffmpeg 的 gdigrab 采集桌面，控制台由 `cmd.exe` 以最大化窗口启动。录制中发现一个环境问题：控制台输出超过可见行数后**停止刷新**，命令继续执行、产物正常写入，但窗口画面停在原处。表现是可复现的：分段脚本输出 37 行时，最后 3 行不再显示。

    ```text
    [现象] seg2 结束时窗口停在 [compare] 行，"== done. ==" 与结束语未出现
    [验证] 同一脚本再次运行，产物 results/demo/replay-1.8.1.json 正常写入，
           说明命令已执行，仅是控制台不再重绘
    ```

17. 处理方式：把演示拆成三段连续镜头，每段输出控制在 30 行以内，分别录制后无损拼接。三段合起来是完整流程，未做画面重绘或时间轴伪造。录制脚本与批处理保留在工程外的工作目录。
18. 录制的三段分别验证了末帧内容：263/263 通过、2 字节反例、以及两版重放与 0 处差异。

## 仍然存在的限制

19. Windows 官方二进制没有插桩，`guided` 模式与边覆盖统计未在本机实测，仅提供 Linux Clang 构建入口。
20. 全面复现的历史缺陷仍是同一处（`locfile.c` 断言）。实验中重复触发次数不计为多个缺陷。
21. 确定性用例覆盖 jq 的常用功能子集，不是完整语义覆盖；用例之外的内建函数没有系统验证。
