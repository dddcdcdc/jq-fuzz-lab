## 最终题目

**《面向事务型键值存储的覆盖引导式模糊测试与崩溃复现平台》**

**待测软件**定为自制的 C++ 命令行程序 **MiniKV**。它从标准输入读取命令脚本，在内存中执行 `BEGIN`、`PUT`、`GET`、`COMMIT` 和 `ROLLBACK`。**测试平台**用 Python 实现，接收待测软件目录，自动生成输入、启动程序、捕获崩溃并输出可重放的缺陷报告。大模型用于辅助设计、编码和调试，平台运行全程可以离线完成。

选择事务型键值存储，是因为它在很小的实现范围内就有三层可测行为。`PUT k 3 abc` 有明确的**命令语法**，声明的 `3` 必须等于实际数据的**字节长度**，提交和回滚则有依赖前序操作的**状态与结果**。尤其是回滚，其正确结果可以直接验证：事务结束后，读取应得到事务开始前的已提交值，原来没有该键时应返回 `NOT_FOUND`。

## 待测软件和平台设计

| 预置教学缺陷 | 触发方式与预期证据 |
|---|---|
| **写入边界导致堆缓冲区越界** | `PUT` 的堆缓冲区有 64 字节，正常最多存 63 字节文本和一个终止符。缺陷版错误接受 64 字节文本，写终止符时越界。平台从短文本种子生成 63、64、65 字节等候选，并同步更新声明长度。 |
| **回滚后读取触发释放后使用** | 正常种子为 `BEGIN → PUT → GET → COMMIT → GET`。把 `COMMIT` 变异为 `ROLLBACK` 后，回滚释放暂存值，但缺陷版漏清理读取缓存，最后一个 `GET` 会访问已经释放的内存。 |

目标目录中的 `target.json` 声明启动命令、种子、超时和正常拒绝码。平台在独立子进程中执行每个样本，分别记录正常完成、输入拒绝、超时、启动失败和崩溃。MiniKV 用 **AddressSanitizer（ASan）** 捕获内存错误，用 **Clang SanitizerCoverage** 采集实际执行的控制流边。覆盖反馈模式把触达新边的样本加入种子队列。首版以 Linux 或 WSL 加 Clang 为演示环境，当前机器仍需准备可用的 WSL 环境。 [Clang ASan 文档](https://clang.llvm.org/docs/AddressSanitizer.html) · [Clang SanitizerCoverage 文档](https://clang.llvm.org/docs/SanitizerCoverage.html)

每条缺陷报告保存原始输入、退出状态、诊断栈和重放命令。平台尝试删除多余命令、缩短字段，每一步都重新运行，确认仍触发同一故障签名，再保存缩减后的反例。

| 测试方向 | 具体怎么测 | 自然涉及的课程思想 |
|---|---|---|
| 脚本解析与错误处理 | 从正常脚本出发，删除括号、截断表达式、修改字符串和函数参数，观察程序如何处理 | 种子变异、基于语法的生成、测试预言 |
| JSON 与参数边界 | 生成空数组、长字符串、深层结构、不同字段类型，再执行相应操作 | 边界值、结构化输入、语义约束 |
| 执行路径探索 | 收集实际运行的代码覆盖信息，优先继续变异带来新覆盖的输入 | 覆盖指标、覆盖引导式测试 |
| 结果正确性与反例分析 | 例如对有界整数数组检查重复排序的结果一致，发现问题后缩短输入并重放 | 性质测试、蜕变测试、反例缩减 |

第二节中的输入变异、文法与约束、覆盖反馈都能直接进入实现。第四节的性质检查与反例缩减，也能承担具体任务。课程中的状态机、符号执行和完整数据流分析，可以按实际需要选取。 《软件安全- 第二节课.pdf》 《软件安全- 第四节课.pdf》

**第一个实验建议固定为 jq 1.8.0 的历史崩溃，并以 1.8.1 作修复对照。** 上游记录显示，某些脚本在文件结尾出现语法错误时，1.8.0 会触发断言崩溃，1.8.1 修复了这个问题。这是实际软件中“错误处理路径本身存在缺陷”的例子，适合用截断、删除和结构化变异重新触发，也比较容易讲清楚根因。 [缺陷报告](https://github.com/jqlang/jq/issues/3348) · [1.8.1 修复说明](https://github.com/jqlang/jq/releases/tag/jq-1.8.1)

平台的主要工作可以这样安排。

1. **接入目标目录。** 目录清单描述 jq 的启动方式、脚本与数据输入位置、正常种子和运行限制。Python 负责组织测试任务。
2. **自动生成并执行。** 实现字节级变异和结构化变异，逐个启动目标进程，结合异常信号、断言信息及 ASan 诊断捕获崩溃。
3. **形成可复核报告。** 保存触发输入、目标版本、运行参数、诊断信息和重放命令，再自动缩减输入，每一步都确认故障仍能复现。
4. **做有控制的比较。** 用同一目标构建、相同初始种子和执行预算，比较字节级变异、结构化变异、结构化变异加覆盖反馈，记录覆盖情况和发现故障所需的执行次数。

这样，项目的主要成果就是你实现的平台，以及平台在真实软件上的实验。选用历史缺陷还允许展示同一输入在缺陷版与修复版上的不同表现。报告应准确写成“自动重新发现已知历史缺陷”，公开反例用于验证环境，正式发现实验从正常种子开始。

**目前已经确认的是上游缺陷与修复记录，本机复现和自动重新发现仍待验证。** 实施的第一步应先跑通这组版本对照，再验证通用变异策略能否在可接受的预算内触发它，之后再扩展 JSON 边界与结果性质测试。
